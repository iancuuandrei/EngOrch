Da. **Aș transforma explicit v1.0.29 în v1.1.0**, dar nu aș mai adăuga încă un subsystem mare. Tema release-ului ar trebui să fie:

> **Fabric v1.1.0 — resilient autonomous execution**  
> Un run nu se termină doar pentru că o optimizare, un format LLM sau o presupunere a plannerului a eșuat. Se oprește numai când continuarea ar fi nesigură sau când taskul chiar nu mai poate fi rezolvat sub politica curentă.

Am auditat codul actual și încă există câteva locuri care merită reparate înainte să numesc v1.1 „închis”.

### Ce aș schimba înainte de v1.1.0

1. **Eliminăm string-matching-ul din failure classification.** Acum `autonomousBlockReason()` decide parțial după `"unknown"`, `"pending"`, `"repair bound"` din textul erorii. E fragil. Toate opririle autonome trebuie să fie erori tipizate cu `GateDisposition` explicit: `DENY / FALLBACK / REPLAN / ATTENTION / PAUSE`.

2. **Eliminăm limitele arbitrare de 64/256 pași.** `RunAutonomous` și graph runner-ul pot ajunge la `autonomous execution step limit reached` chiar dacă produc progres. Aș folosi progress detection pe journal head/state + un transition budget derivat din numărul taskurilor și repair budget. Dacă există progres valid, continuăm; dacă nu există progres, `NEEDS_ATTENTION`, nu crash arbitrar.

3. **Bounded correction pentru output LLM invalid.** Acum un planner/writer/reviewer poate avea un turn complet și confirmat, dar dacă JSON-ul, graph-ul, anchor-ul sau verdictul sunt invalide, run-ul se poate opri. Dacă provider effect-ul este complet cunoscut și nu s-a aplicat nicio mutație, Fabric ar trebui să permită un **nou correction turn cu identitate nouă**, nu să retry-uiască turn-ul vechi:
   - planner graph invalid → „correct only these validation defects”;
   - writer proposal invalid/anchor invalid → proposal correction;
   - reviewer verdict malformed → verdict correction.
   
   Aș da maximum 1–2 correction turns/role, separat de semantic repair budget.

4. **Automatic candidate-bound replan pentru `NEEDS_REPLAN`.** Acum statusul este corect, dar cere operator. Aș implementa:
   
   ```text
   scope expansion requested
            ↓
   candidate-bound read-only replan
            ↓
   preserve completed tasks
            ↓
   graph revision N+1
            ↓
   validate new ownership
            ↓
   continue
   ```
   
   Fără auto-replan dacă există `UNKNOWN`, pending effects sau candidate ambiguity.

5. **Observability nu trebuie să arunce un rezultat semantic bun.** În Codex adapter există două cazuri concrete pe care le-aș schimba:
   
   ```go
   recordReadbackCompaction(...) error
       → currently loses the completed result
   ```
   
   Compaction evidence este observability/qualification, nu correctness authority. Dacă turn-ul este complet și result identity este valid, marchezi compaction evidence `UNKNOWN/UNAVAILABLE`, dar păstrezi rezultatul.
   
   La fel `attachUsage()` poate actualmente invalida rezultatul. Dacă usage-ul nu este necesar pentru un hard budget, păstrezi result și marchezi usage unknown. Dacă este necesar pentru budget authority, păstrezi rezultatul deja produs, dar oprești **următorul provider call** până la reconciliere — nu arunci munca deja făcută.

6. **Context-tool burst handling.** Broker-ul permite `MaxCalls: 64`, dar FIFO-ul proaspăt are 1 active + 32 waiting; un model care emite un burst legal mai mare poate primi HTTP 429. Aș lega queue capacity de invocation call budget și aș separa:
   
   ```text
   queue wait deadline
   ≠
   execution deadline
   ```
   
   astfel încât timpul petrecut așteptând să nu consume tot callback timeout-ul. Un burst legal de tool calls n-ar trebui să omoare run-ul.

7. **Optional reviewer/context intelligence trebuie să degradeze și mid-run.** v1.0.29 rezolvă foarte bine RI absent *înainte* de run. Mai trebuie aceeași filosofie dacă review-impact collection sau semantic context eșuează ulterior:
   
   ```text
   advisory RI unavailable
       → plain candidate review
   ```
   
   Dar candidate substitution / path escape / source drift rămân `DENY`.

8. **Cache corruption trebuie împărțită în două.** Un cache entry derivat, într-un root sigur, care este malformed/corupt poate fi quarantined/deleted + recomputed. Un unsafe root, reparse/symlink escape sau identity-domain substitution rămâne hard fail. Cache-ul este advisory; nu merită să pierzi run-ul din cauza unui `.json` corupt.

9. **Verification toolchain failure trebuie detectată înainte de model spend.** Executable-ul/check environment trebuie preflight-uit cât mai devreme. Dacă `go` nu există, mai bine refuzi înainte de planner decât după 400k tokens. Verification semantic failure rămâne normal repair evidence.

10. **Dynamic RAM adaptation**, dar numai la admission. Aș observa available RAM/RSS și aș reduce numărul de **noi** workers cu hysteresis:
   
   ```text
   memory pressure ↑
       → stop admitting writer C
       → A/B continue
       → maybe serial afterwards
   ```
   
   Nu omorâm workers aflați în execuție pe baza unui heuristic. Toate deciziile sunt înregistrate ca scheduling evidence.

11. **`doctor` ar trebui să arate Effective Execution Plan.** Înainte de provider calls:
   
   ```text
   RI             go-contract-v3 → available
   writers        isolated 3 → fallback serial (low RAM)
   cache          enabled
   compaction     disabled (Muse unsupported)
   verification   3/3 commands preflight OK
   runtime        Muse/OpenCode qualified
   ```
   
   Userul vede dinainte ce se va întâmpla.

12. **`execution_blocked` generic trebuie aproape să dispară.** La final ar trebui să existe o taxonomie mică și clară:
   
   ```text
   READY
   PAUSED
   NEEDS_ATTENTION
   NEEDS_REPLAN
   NEEDS_RECONCILIATION / UNKNOWN
   UNSAFE
   ```
   
   `UNSAFE/UNKNOWN` sunt hard. Restul păstrează candidatul și dau un next action concret.

### Aș da lui Sol următorul goal exact așa:

# Fabric v1.1.0 — Resilient Autonomous Execution Closure

Turn the current integrated Fabric v1.0.29 into a release-quality **v1.1.0** focused on resilient autonomous execution, graceful degradation, predictable recovery, and measured efficiency.

The purpose of this increment is **not to add another major intelligence subsystem**. The purpose is to remove avoidable ways in which an otherwise viable engineering run can terminate because of optional capability failure, model-output formatting defects, rigid planner assumptions, bookkeeping/observability failure, arbitrary controller bounds, or resource-pressure conditions.

Use current `main`/`dev` as authoritative. Preserve all historical journals, UNKNOWN effects, releases and evaluation evidence. Do not revive G0/self-hosting or resend any uncertain historical effect.

## Core principle

Fabric must:

**fail closed on authority, fail soft on capability, and preserve useful engineering state on failure.**

Hard safety boundaries remain strict:

- repository/source/candidate identity;
- safe paths and filesystem containment;
- credentials and runtime identity;
- exact effect ownership;
- journal integrity;
- uncertain or duplicate external effects;
- candidate-bound verification/review;
- mutation outside admitted ownership unless a new scope is explicitly replanned and admitted.

Everything else must be audited for graceful continuation.

## Mandatory audit

Audit every path that can terminate `run --autonomous` or `resume --autonomous`, including:

- preflight/configuration;
- planner/context admission;
- RI and semantic evidence;
- task graph validation;
- scheduler/resource admission;
- explorer/tool calls;
- writer proposal decoding and anchored edits;
- reviewer verdict decoding;
- repair planning/budget;
- isolated/parallel writers;
- cache read/write/eviction;
- native compaction observation;
- usage accounting;
- verification setup and execution;
- journal/runtime reconciliation;
- pause/resume;
- CLI failure classification.

Classify each terminal condition as one of:

`DENY`, `RECONCILE`, `REPLAN`, `ATTENTION`, `FALLBACK`, or ordinary success/progress.

Remove string-based error classification from autonomous product behavior. Use typed errors/outcomes carrying an explicit disposition, safe public reason, candidate-retention state and next action.

## Required product changes

### Progress-aware autonomous execution

Replace arbitrary fixed controller step limits as ordinary user-visible terminal failures.

Track durable progress using controller/journal identity and state transitions. Derive any defensive transition bound from the admitted graph, task count and repair/replan budgets. If the controller cannot make progress, produce a typed retained-state outcome instead of an unexplained step-limit failure.

### Bounded model-output correction

A completed and receipt-bound provider invocation whose semantic output is invalid but whose external effect is fully known must not automatically destroy the run.

Add bounded, versioned correction turns for:

- invalid planner/task-graph output;
- malformed writer proposals or invalid anchors that were not applied;
- malformed reviewer verdicts.

A correction is a **new invocation with its own identity**, never a resend of an uncertain invocation.

Correction must preserve candidate, objective, previous output evidence and exact validation errors. It must not authorize mutation or silently widen scope.

Keep a small separate correction budget so protocol/format repair does not unnecessarily consume the semantic code-repair budget.

### Candidate-bound automatic replan

Implement bounded automatic continuation from `NEEDS_REPLAN`.

A replan may occur only when:

- the current candidate is confirmed;
- no pending or UNKNOWN effect exists;
- the rejected proposal/scope request is durably known;
- completed task/effect evidence can be preserved.

The replanner receives the current candidate, existing graph, completed tasks, rejected scope request, relevant verification/review evidence and engineering intelligence.

It may produce a new graph revision and explicit ownership changes. It must preserve completed valid work where possible.

It must never silently grant a writer new paths.

UNKNOWN or ambiguous execution state always requires reconciliation before replan.

### Optional context/review degradation

Extend v1.0.29 graceful behavior into mid-run advisory intelligence.

Failure of optional semantic/context/reviewer-impact evidence may fall back to a lower-capability but admitted context/review path when the failure does not indicate source/candidate substitution or unsafe filesystem state.

Identity drift, provenance mismatch and unsafe paths remain DENY.

### Runtime metadata must not erase completed semantic work

Audit Codex/OpenCode completion paths.

Compaction lifecycle observation, usage accounting and other non-authoritative diagnostics must not discard a completed, identity-valid semantic result merely because optional metadata could not be normalized.

If accounting is required for future budget authority, preserve the completed result and block only subsequent provider dispatch until the accounting condition is reconciled.

Never reinterpret missing usage/cost as zero.

### Context-tool burst resilience

Align context-tool transport admission with the invocation's actual bounded tool-call budget.

A legal burst of context calls must not fail merely because transport queue capacity is smaller than the admitted call budget.

Separate bounded queue-wait time from callback execution time and retain FIFO, duplicate-ID and shutdown guarantees.

Do not create blind tool retries or new request IDs for uncertain calls.

### Cache degradation

Derived cache data is not authority.

Within a verified safe cache root, malformed/corrupt derived entries should be quarantined/removed and recomputed where safe.

Unsafe cache roots, reparse/symlink escapes, identity-domain substitution or policy tampering remain DENY.

Cache permission, capacity and ordinary storage failures should degrade to recomputation whenever safe.

### Verification preflight

Move all deterministic verification-environment failures that can be known before provider work as early as possible.

Do not spend model calls only to discover that a required verification executable cannot start.

Semantic test failures remain normal engineering evidence and may trigger repair.

### Memory-aware admission

Add conservative live memory-pressure adaptation to scheduling.

Use observed available memory/process pressure only to control **future admission**:

- reduce parallel admission under pressure;
- fall back toward serial execution;
- use hysteresis to avoid oscillation;
- record the observation and scheduling decision.

Do not kill or revoke already admitted model/effect work because of a heuristic memory sample.

Do not present memory estimates as measured facts.

### Effective capability plan

Extend `doctor` or add an equivalent read-only inspection that shows the effective pre-dispatch configuration:

- selected runtime/model roles;
- RI/context mode and fallback;
- writer topology;
- resource capacity/admission;
- cache status;
- compaction status;
- verification executable readiness;
- expected degradation choices.

No provider call is required for this projection.

## Efficiency work

Profile actual current Fabric workloads before optimizing.

Measure at minimum:

- stage wall time;
- Go allocations;
- process RSS/peak where reliably observable;
- RI startup/query time;
- context compilation;
- candidate capture/hash time;
- journal replay/inspection;
- tool queue wait;
- verification setup/runtime;
- typed provider token usage.

Use at least:

1. a normal successful task;
2. a task requiring repair;
3. a parallel/isolated task.

Only integrate optimizations with measured benefit and no correctness regression. Do not add speculative caches or duplicate indexes.

## Required failure semantics

A user-visible autonomous run should converge to a small explicit set of states:

- `READY`
- `PAUSED`
- `NEEDS_ATTENTION`
- `NEEDS_REPLAN`
- `UNKNOWN` / reconciliation required
- `UNSAFE`

Avoid generic `execution_blocked` when a precise typed condition is known.

`NEEDS_ATTENTION` and `NEEDS_REPLAN` preserve the candidate and useful evidence.

Neither status implies acceptance.

## Required fault-injection qualification

Create deterministic regression coverage demonstrating at least:

- missing optional RI → bounded source fallback;
- unavailable isolated/parallel execution → serial fallback;
- unsupported compaction → disabled;
- cache permission/capacity failure → recompute;
- corrupt safe derived cache entry → recompute;
- legal context-tool burst → no run-level failure;
- invalid planner output → bounded correction;
- invalid unapplied writer proposal → bounded correction;
- malformed reviewer output → bounded correction;
- legitimate scope expansion → candidate-bound replan;
- exhausted repair budget → retained `NEEDS_ATTENTION`;
- lost non-authoritative usage/compaction metadata → semantic result retained as permitted by policy;
- missing verification executable → pre-dispatch failure;
- uncertain external effect → DENY/reconcile without resend;
- identity/path/journal substitution → DENY.

## Release acceptance

Do not rename or release v1.1.0 merely because implementation is complete.

The exact final source must pass:

- complete fresh Go suite;
- complete applicable Rust workspace suite;
- PowerShell evaluation harnesses;
- Sonar/security;
- independent review;
- fault-injection/graceful-degradation suite;
- reproducible Windows packaging.

Run applicable hosted/provider/SCIP qualification rather than silently counting it as pass.

Perform a fresh installed-binary real coding task on the exact release candidate.

Perform a fresh Muse/OpenCode real task using the exact final release candidate, not an earlier dirty/custom binary.

Run one fresh unchanged canonical engineering cohort on the exact v1.1.0 candidate. Target:

**fixed-six 6/6 + godotenv PASS + generated-code ownership PASS = 8/8 in one cohort.**

Do not pool passing rows across historical versions.

If 8/8 is not achieved, retain the exact failure and determine whether it exposes a genuine Fabric defect or model/task-quality limitation before changing product behavior.

## Non-goals

Do not add:

- another graph/vector database;
- speculative JEV;
- generic conversation memory;
- a new sandbox platform;
- multi-repository engineering;
- broad provider infrastructure;
- governance-only machinery.

The v1.1.0 goal is to make the sophisticated system Fabric already has **resilient, predictable, efficient and pleasant to use**.

A normal user should almost never lose a viable run because an optional mechanism failed.

A run should stop abruptly only when Fabric can state a concrete reason why continuing would risk correctness, authority, or an unresolved external effect.

Asta este, în opinia mea, **cea mai bună utilizare a următorului ciclu de dezvoltare**.

Dacă iese cum trebuie, aș publica direct **v1.1.0**, nu v1.0.30. Diferența conceptuală este suficient de mare: v1.0.x a construit capabilitățile; **v1.1.0 face orchestratorul rezilient ca produs**.
